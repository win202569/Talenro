## Approaches and proposed choice

User selected independent output with old artifacts retained. Within that scope,
recommend a fixed App-only variant following the existing account-center pattern.
Reusing ordinary/close-stage paths would overwrite old evidence. Global arbitrary
output overrides risk propagating to Core and NuGet imports; do not use them.
A separate worktree duplicates environment preparation and is unnecessary here.
The exact property/path names below were included in the approved design.

## Fixed isolation contract

- New property OrdinaryBuildVariant: empty (unchanged defaults) or account-center.
- Fixed App paths: bin/ordinary-account-center/ and obj/ordinary-account-center/;
  MSBuildProjectExtensionsPath is the absolute selected App obj path.
- Selected variant requires Debug; EnableLayoutDiagnostics=false,
  EnableEmailGeometryRecording=false, EnableCloseStageRecording=false;
  EmailGeometryBuildVariant and CloseStageVerificationMode both empty.
- Reject unsupported/path-like values and incompatible combinations in an App
  initial validation target before restore, with distinct ORDINARYBUILD001 error.
- Keep all existing guards; Core/Tests property/output behavior remains unchanged.
- Do not pass RuntimeIdentifier or arbitrary output paths globally. App retains
  its own win-x64 RID; Core retains empty RID. Do not copy project.assets.json.
- No source/layout/business change, new observer or launch entry in this scope.

## Proposed stages and acceptance checks

### 1. Configuration and isolation verification (separate implementation approval)

Future files: clients/windows/Directory.Build.props,
clients/windows/Talenro.Demo.App/Talenro.Demo.App.csproj and a focused
clients/windows/Talenro.Demo.Tests/OrdinaryBuildIsolationTests.cs.

Test first: exact App paths/absolute extensions path, absent diagnostic defines
and compile payload, unchanged empty-variant behavior, unchanged Core/Tests paths.
Negative cases: unknown/path-like value, Release, each enabled diagnostic switch,
nonempty email variant, nonempty close verification. Require ORDINARYBUILD001,
not an unrelated missing-target or restore error. Evaluate only during these
configuration tests; no native App build/restore. Preserve existing isolation tests.
Detailed execution checklist follows design approval, before implementation.

### 2. One local locked restore and conditional native build (new explicit authority)

Before writes: committed clean sources; ordinary Windows token; successful query
showing no relevant App/prototype/build/test processes; available installed tools;
both proposed App bin/obj destinations absent and no reparse ancestors. Stop on
existing paths, failed query or missing dependencies; do not delete or reuse them.

Inventory all preexisting App output files (including copied dependencies/XBF),
App/Core lockfiles and existing raw observation receipts by relative path/size/hash.
Store the inventory outside those protected trees. Preserve prior files unchanged.
Core's default bin/obj may be regenerated by dependency compilation: inventory and
snapshot relevant existing Core outputs/restore records first, verify snapshot
hashes, and explicitly include these bounded writes in later approval. Do not
promise total workspace output isolation or unchanged default Core artifacts.

Read-only evaluation must show exact selected App paths and unchanged Core RID/
paths. Use only existing package cache with a dedicated local-only NuGet config;
locked restore, no downloads/lock edits/audit suppression. Verify metadata content
hashes against lock entries and archive hashes against their own sidecars; do not
confuse these hash domains. Keep offline vulnerability-data warnings visible.

Proposed budget: one restore, then one no-restore build only after restore exit0,
unchanged lockfiles and expected asset-source/output inspection. Same fixed
properties in both commands. Each at most300s observed in intervals <=30s; failure
or timeout stops downstream work, no automatic retry or process termination.
Keep the original session to observe an outstanding command; timeout is not exit.
App obj may exist from this authorized restore; App bin must still be absent
before the first native build. No actual commands are authorized by this document.

### 3. Static inspection and preservation

Treat binaries only as data: PEReader/metadata, no Assembly.Load, app execution,
UI automation or invoking its entry point. Record exact source commit, effective
configuration, tool versions, EXE/DLL/Core/XBF/deps/runtimeconfig sizes and SHA256.
Require expected x64 target, copied Core identity matching the build dependency,
and no LayoutPresentation/LayoutWindowObserver/EmailGeometry/CloseStage payload
or diagnostic fixture resources. Retain ordinary reserved-option rejection code.

Require generated Account XAML contains Center on the intended shared panel;
match generated/deployed Account XBF hashes and correlate generated-file inventory
with this build. Do not treat XAML alone, a changed XBF hash, or a diagnostic DLL
as proof about ordinary deployed layout. Inspect all App generated paths for
escape into preserved output directories. Rehash old artifacts/receipts/lockfiles
and require equality; report bounded Core output changes separately.

Success yields an inspected ordinary Debug candidate, not proof of visual fit,
normal shutdown, reserved-option runtime rejection, security clearance or C4.
No launch allowance is granted. Later native checks require their own fixed
artifact binding, finite approval and normal-close observation.
