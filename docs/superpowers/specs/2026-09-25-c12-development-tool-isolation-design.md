# C12 开发工具依赖隔离设计

日期：2026-09-25。状态：待用户审阅；已批准方案方向，尚未批准本文或实现计划。

## 1. 目标与证据边界

目标是在保留依赖完整性校验、Windows 隔离机制及原有验收时限的前提下，
将不参与 C12 运行、测试或数据库迁移的开发工具依赖移出主模块。
用户希望继续完成 C12 验收，而不是绕过检查或修改业务架构。

依据：[2026-09-24 诊断记录](../../roadmap/2026-09-24-docker-acceptance-diagnostics.md)。
当前根模块同时登记六个工具；sqlc v1.31.1 的模块声明引入 doubleclick v1.0.0，
后者本地目录包含 127,449 个文件。经用户批准的 Defender 录制确认，
目标诊断进程触发了大量打开文件时的实时扫描。正式准备阶段两次超时，
独立 15 分钟预校验亦未完成。

这些证据支持减少无关工具依赖参与校验，但不证明隔离后一定满足时限，
也不能解释历史取消响应超限、CreateProcessW 拒绝和其他普通测试失败。
本文不承诺已经消除验收阻塞。

## 2. 选择与排除的方案

采用：主模块与一个独立开发工具模块分离，工具仍完整锁定和验证。
相对逐工具拆分，一个开发工具模块足以切断对主模块的工具依赖引入，
避免本轮增加多个模块和复杂分派规则。

暂不采用：换 Windows 机器（不能保证消除同类开销）；Linux 替代验收
（现有 runner 依赖 Windows ACL、Job 和进程身份机制，并非等价替换）。
不采用：删除缓存文件、移除第三方 testdata、关闭防护、设置排除项、
放宽时限、用先前成功缓存替代当前完整性验证。

## 3. 模块边界

| 内容 | 归属 | 要求 |
| --- | --- | --- |
| 业务、普通测试、integration 测试依赖 | 根 go.mod/go.sum | 保留实际需要的全部依赖 |
| Goose 库与 Goose CLI 3.27.1 | 根模块 | 迁移及集成测试均使用；本轮不迁移、不改驱动集合 |
| Buf 1.72.0 | tools/devtools/go.mod/go.sum | 完整保留代码生成依赖 |
| protoc-gen-go 1.36.11 | 开发工具模块 | 与现有生成版本一致 |
| oapi-codegen 2.8.0 | 开发工具模块 | 不迁移业务使用的 oapi-codegen/runtime |
| sqlc 1.31.1 | 开发工具模块 | 保留 doubleclick 等工具所需依赖 |
| golangci-lint 2.12.2 | 开发工具模块 | 分析对象仍是根模块，不是工具模块 |

新模块路径固定为 `talenro.local/devtools`，Go 版本维持 1.26.0，
工具链维持 go1.26.5。不建立 go.work，不添加主模块到工具模块的 require/replace，
也不让工具模块 require/replace 主模块。两个模块共享物理下载缓存不是问题：
校验范围应由各自真实模块图决定，不能靠删除缓存来缩小范围。

根模块保留 Goose 的 tool 指令和所有实际所需库。不能为了移走命令行工具，
误删 protobuf、kin-openapi、Goose 等仍被源码引用的库。
只能基于完整模块图和包依赖分析移除工具专属依赖，不能按名字黑名单删条目。

锁版本原则：不升级任何顶层工具或保留的根依赖。对迁移前后选中的传递版本
逐项比较，避免拆分和 tidy 导致隐式降级；新工具模块需显式保留工具闭包中
原来选中的版本。任何无法在不改语义的前提下保留的版本差异须报告并单独审批。

## 4. 调用与兼容性

开发工具通过显式备用模块文件调用，例如在仓库根目录执行：

```text
go tool -modfile=tools/devtools/go.mod sqlc generate
go tool -modfile=tools/devtools/go.mod golangci-lint run ./...
```

本地固定 Go 1.26.5 的 tool 实现明确支持 -modfile；实现阶段仍需验证子工具
工作目录与环境行为。参数只用于选择工具构建依赖，不能作为全局 GOFLAGS
传入分析目标或生成的子进程。生成器和 lint 的工作目录始终是仓库根目录；
路径包含空格时，PowerShell/Bash 必须按独立参数传递，不拼接可执行字符串。

更新两个平台的 generate、check-tools 和 verify-c11 工具调用。
保持现有公开脚本入口、退出码、输出脱敏、超时和清理行为。
`buf.gen.yaml` 中的嵌套 protoc-gen-go 调用必须显式选择同一工具模块，
不能悄悄退回根 tool 表或 PATH 中未锁定的二进制。
Goose、smoke 的迁移命令和 C12 runner 的 Goose 调用维持原样。

兼容性变化需要明示：根目录裸 `go tool sqlc` 等五个已迁移工具命令不再受支持；
用户改用已有公开脚本或文档中的显式 -modfile 命令。根目录 `go tool goose` 保持。
不得为维持裸命令而重新把五个工具挂回根模块。

## 5. 校验强度与阶段划分

根模块继续使用完整的 `go mod verify`，不是只验压缩包、抽样模块或文件。
C12 runner 的模块图来源、候选树绑定、文件哈希、构建前重验证、离线策略、
环境白名单、进程隔离和资源清理都保持不变。本轮不改其执行代码。

开发工具模块必须有独立完整验证阶段。新增配对入口
`scripts/verify-devtools.ps1` 和 `scripts/verify-devtools.sh`：

- 以明确的工具模块目录运行完整 go mod verify，GOWORK=off；
- 非零退出、缺依赖或超时均返回失败，不能静默跳过或退回联网；
- 不运行生成器、不启动 Docker、不清理用户缓存、不打印原始敏感输出；
- 在受控验收执行阶段采用固定工具链、只读模块和离线配置；下载依赖另属准备阶段；
- 独立默认 15 分钟上限，达到上限即阻塞开发工具验证，不自动重试或延长；
- 两个平台必须停止其自己启动的进程树并准确传播失败，不借此扩展 C12 清理权限。

开发工具验证必须在代码生成、工具版本检查及完整 C11 工具链流程的受支持入口中
先成功，才执行后续工具；各公开入口独立承担验证责任。嵌套入口可能重复验证，
本轮接受这一成本，不新增跳过参数或可跨运行复用的“已验证”标志。
若该成本导致完整流程超时，必须如实报告，不能静默去掉验证。

这不是免除工具验证，而是把其成本放在实际使用工具的阶段。
C12 专项验收可以独立记录物理测试结果，但完整开发工具验证若仍失败，
项目整体验收不得标记通过或据此合并 main。

不声称已减轻 Goose 保留依赖带来的开销；例如 wazero 是否仍被根模块图选中，
必须以拆分后模块图确认。若主模块仍无法满足原定预算，停止并报告，不继续扩大拆分。

## 6. 变更范围

允许的实现范围：根 go.mod/go.sum；新增 tools/devtools/go.mod/go.sum；
generate、check-tools、verify-c11 的 PowerShell/Bash 入口；新增上述开发工具验证入口；
buf.gen.yaml；相关脚本隐私、工具版本、调用契约、模块边界测试；README、
恢复运行手册和当前状态文档。

重点回归 `internal/e2e/privacy_test.go` 的假工具分派、命令顺序及输出脱敏断言，
不能只改假工具使测试变绿。补充真实工具版本和生成结果验证。
生成文件预期零变化；一旦发生变化，先调查，不能顺手接受重生成差异。

不改生产逻辑、SQL 迁移、C12 控制器/授权接口、runner 安全协议、Docker 资源模型。
诊断程序和原始 ETL 只在忽略目录保留，不加入提交。历史设计保留原文，
当前手册明确说明新的工具调用方式，避免抹掉历史验收事实。

## 7. 必须取得的验证证据

1. 模块边界：普通及 integration 包依赖、Goose CLI 构建闭包完整可解析；
   证明工具专属依赖只因边界正确而消失，不能仅凭文件行数减少判断成功。
2. 版本：两个模块选中版本与隔离前基线对照；六个工具版本输出仍符合原合同。
3. 负向校验：用专属临时模块/缓存测试缺失、篡改、错误退出和超时必失败；
   不篡改用户共享缓存。禁止把工具验证成功代替主模块验证，反之亦然。
4. 脚本：PowerShell/Bash 路径含空格、退出码、环境恢复、离线失败及脱敏；
   Buf 的子工具调用和 lint 分析根模块的行为必须覆盖。
5. 内容：完整生成执行后，受版本控制的生成内容无差异；工具模块验证未完成时
   不得将版本检查或 fake harness 通过当成工具链验收。
6. 普通回归：运行批准计划中的完整普通测试与相关 focused 测试，保留历史失败记录。
7. C12：独立执行原批准的 13 项物理调用，每项原 5 分钟测试预算、原准备预算，
   要求真实 PASS、无 Skip 替代，并验证既有清理和 foreign-canary 断言。
8. 性能：报告根模块完整验证的实际时间和环境。缓存后的快速通过不等于可重复冷态性能；
   不清空共享缓存伪造冷态。若稳定性未证实，明确保留风险。

上述条件均不能以“工具已经移出去”为由跳过。任何工具链阶段或物理阶段未完成，
仍只可记录未验收开发检查点；main 合并需要全部适用验收及独立明确授权。

## 8. 风险、回退及审批

主要风险是工具运行目录错误、隐式版本变化、Buf 子命令选择错误、主模块仍有重依赖，
以及仅将超时从 C12 转移到生成阶段。测试和状态报告必须显式覆盖这些风险。

回退应按独立提交反向恢复模块声明与脚本，不删除共享缓存、不重置用户工作区，
也不把回退视为历史阻塞已解决。

计划获批并确定执行方式后才开始代码变更。当前 I2（物理验收）和 I3（历史测试失败
原因）仍开放。本设计不是实现完成或安全审查通过的声明。
