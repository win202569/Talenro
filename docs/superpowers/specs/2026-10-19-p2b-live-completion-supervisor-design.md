## 1. 意图与范围

解决离线诊断控制器反复出现的共同问题：把磁盘记录当作下一步权限，同时把
资源清理与最终记账绑在一起。成功标准不是再调整一行保存顺序，而是：

- 磁盘存在完整的成功记录，但没有存活监督器的正向确认，仍不能启动下一步。
- 已知失败的台账不因 finally、汇总、发布或“修复记录”再次进入文件访问。
- 拒绝记账不能阻止确切拥有进程的有限清理，也不能覆盖实际首因。
- 换机能恢复源码、证据、限制和待办，不能恢复旧运行权限或重复已消费额度。

本设计是固定离线夹具的串行运行控制层，不是生产握手协议、产品 capability、
Windows Job/独立 watchdog、真实安全前提验证或持久化事务系统。它不取代既有
[真实采集/独立监督设计](2026-10-17-raw-capture-supervision-design.md)，
也不实现[生产握手消费合同](2026-10-19-p2b-handshake-contract-design.md)。
SourceVerified/LiveActionsPerformed/RuntimeApproved/FormalAcceptance/
RealGateImplemented 仍为 false；不合并 main，不发布、不安装、不改安全设置。

## 3. 选型与取舍

选定：每个获准的固定运行序列由一个存活监督器拥有步骤顺序、实际进程观察、
出口健康表和完成确认。不同的独立序列不继承确认。运行文件只作证据；跨独立
shell 调用不得从文件恢复控制器内存状态。

未选方案：仅添加确认文件/最终 rename，仍不能单凭文件存在证明产生它的操作
正常返回；数据库/独立确认服务可承载另一种持久化恢复设计，但增加组件、故障
模型和权限，不在此范围。这里明确牺牲自动跨会话恢复，以换取可论证的拒绝继续。
不声称原子文件操作没有价值；它们只是不替代本设计所需的存活正向确认。

## 4. 组件与唯一所有者

| 组件 | 唯一职责 | 不得承担 |
| --- | --- | --- |
| 存活监督器 | 私有 Session、步骤表、一次性确认表；检查全部启动门并直接监督其拥有的步骤进程 | 从 JSON、退出文字或调用者自填 bool 构造放行权限 |
| 受控步骤执行器 | 固定批准的夹具目录/参数；其直接子进程的实际退出、双流及有限清理 | 自报完成即授权监督器进入下一步 |
| 出口管理器 | 固定路径及写入者归属、文件操作边界、永久失败标记、拒绝后续访问 | 在失败后重建/覆盖/重试该出口 |
| 观察与便携交接 | 保存实际观察、unknown、哈希及原始字节 | 恢复 Session、确认引用、预算或真实运行能力 |

直接拥有哪个 Process，就对哪个实际对象负责；不以 PID/名称重找、杀树或查询
无关进程。顶层监督器直接观察步骤进程；步骤内部的子进程观察来自冻结执行器
及完整证据校验，必须与顶层直接 OS 观察区分，不能声称顶层独立看见所有后代。

每个步骤唯一写入者的文件在成功关闭、步骤正常完成前不能被另一进程更新。
子进程没有监督器的私有 Session/确认引用；它只能交付候选观察。若步骤异常退出、
报告控制器记账失败或结果不明，监督器停止并隔离该步骤的候选输出集合，不从
其中一份看似成功的文件反推写操作正常返回。

## 5. Session 与完成确认

Session 必须在单个持续存活的运行上下文中拥有，不把多次 exec 命令假设成同一
PowerShell 内存。以后实施计划须明确该宿主及其启动/存活/结束如何计入新预算。
本规范现在不启动该宿主，也不假设已有 API 保证它跨工具调用存在。

Session 的私有状态至少包括：批准范围/固定步骤表、冻结身份、当前步骤、预算
消费、首因/有限次因、出口表、直接拥有的未收束对象、确认登记及不可逆失败位。
公开摘要只是副本，不能把反序列化摘要传回后变成活 Session。

Session 状态只有 New → Active → Closed，或 New/Active → Failed → Closed；
Failed 不可回到 Active，Closed 不可复用。任一控制器故障/unknown/漂移使其 Failed，
撤销全部未消费确认，禁止后续目标启动；清理路径仍可继续。

完成确认是监督器私有登记中的一次性内存身份，不是磁盘 token、随机字符串、
哈希、声明 Verified=true 或产品能力。它绑定所属 Session 的实际身份、固定步骤
序号和冻结输入代次；确认不能跨会话、跨步、跨代次或重复使用。

下一步入口同时检查 Active、无控制器失败、步骤顺序/剩余额度、冻结身份及前步
确认登记；在同一串行控制路径中先消费确认并预消费本步，再做启动前 I/O。
首次步骤由明确批准的新会话入口及完整启动前校验初始化，不由旧文件授予确认。
伪造同名字段、复制/反序列化对象、旧会话引用或已消费引用一律拒绝，且不 Start。
这是私有控制流约束，不是对同进程任意反射/恶意代码的安全沙箱保证。

## 6. 一次步骤的完成顺序

固定顺序是：

1. 检查会话、批准范围、固定输入、确认和剩余额度；预消费本次尝试。
2. 准备固定输出与启动记录。失败或不明则不 Start，尝试仍已消费。
3. 执行固定步骤；及时接上两条原始字节排空路径，实际拥有对象始终保留。
4. 无论正常/异常，先完成允许范围内的终止、有限退出等待、双流收束和 Dispose。
5. 检查实际退出/双流、完整字面 oracle、原始字节/哈希、全部后置冻结项和出口状态。
6. 完成全部规定文件、输出及 flush/关闭；每一操作必须被实际调用方观察为正常返回。
7. 当所有会失败的完成动作均正常返回且 Session 仍 Active，监督器才登记本步确认。
   不在 finally 中授予确认；不先设置确认再进行保存/正常输出。
8. 下一步只能通过同一监督器入口消费该确认；末步则结束本次序列，不再启动目标。

确认登记后不得再执行属于该步成功合同的正常发布/文件写入。任何仍必需的
关闭、进度输出、后置检查必须在第7步前完成。若调用链尚有异常边界，必须在
确认可消费前返回监督器并再次检查存活失败状态，不允许 finally 把失败改成完成。

文件可记录候选成功或已观察到的完成，但这只是证据。尤其是第6步后段写入
报错却留下完整成功 JSON 的 C1 情形：第7步没有确认，第8步必拒绝。新进程即使
读到完全相同的成功文件，也没有原会话确认，不得走续跑入口。

## 7. 出口健康表：失败后不可再访问

新控制器对自己管理的台账、回执、采集文件及最终发布出口，登记固定路径、
唯一写入者、状态和实际操作观察。状态 Healthy → Failed，Failed 不可重置。
同一规范化登记路径只对应一个状态，禁止换拼写、换 API 或换调用方绕过它。
范围是固定私有工作区，不把词法路径比较宣称为针对恶意重解析点的安全边界。

一次完整访问的正常返回包括其规定的序列化、读/解析、写、flush及资源关闭。
任一访问失败/结果不明先锁存真实错误并标记出口 Failed，同时使运行 Session 失败。
一旦调用方获知失败，对该出口的后续 Read/Parse/Save/Complete/Publish/重新打开
均在文件 I/O 前拒绝，不再读取“确认现在好了没有”，也不重建/替换旧文件。

这里的“不重试”是控制器不发起第二次逻辑访问/发布，不声称能取消已经进入
文件库内部的系统调用，或禁止操作系统自身的关闭行为。一次失败操作中必须
释放已持有的资源，关闭异常可保留为次因；不得为了关闭再显式执行 Write/Flush
重试或重新打开文件。不得把重新序列化/Complete 包装成“资源清理”来规避拒绝。

普通进程清理不得依赖台账健康：先保留首因，再收束确切对象；finally 查出口表
后跳过失败台账的最终发布。C2 的第二次 Complete 必须不进入读取/写入。
从失败文件旁新建替代台账、覆盖错误原件或恢复到 Healthy 同样不允许。

必要的独立诊断出口只能按未来计划预先固定并有界尝试；不授予正常步骤继续的
权限。若该诊断出口也失败，将其隔离并停用；不能无限寻找新文件记录日志失败。
现有错误流仅 best-effort、有限摘要；错误流失败也不重试，不保证能持久化报告。
运行结束后，单独获准的只读取证/便携交接可检查剩余原件，但不能据此恢复会话。

## 8. 首因、预期负例及 unknown

真实控制器首次 ErrorRecord 直接锁存，不用序列化文本或自动 Error 列表包装器
替代身份；最多保留8个不同引用的次因，第9个置 overflow。同一记录不重复添加。
清理、输出、最终记录错误不能覆盖首因，overflow/unknown 不可升级成功。

固定夹具的预期 exit1、超时等是冻结计划明确列出的被测结果，不自动等于控制器
故障。负例使用独立、明确归属的被测状态；监督器自己的持久化/输出失败永远
不能因为“本来就是 RED”而当作预期通过。缺原件、坏 JSON、退出/双流不明或
不在完整 oracle 内的错误均停止，不能重建记录或临时放宽预期。

全部出口失效时只能保留存活内存中的失败及尽力错误流输出；监督器死亡后这份
确认也消失，保守地失去继续能力。没有落盘保证，但也不会从残留文件重建确认。
这不是硬实时/掉电恢复或监督器死亡时所有子进程必定退出的证明。

## 9. 旧运行助手的显式兼容性决策

旧 owned-run.ps1 在首次 Save-Receipt 失败后，会在 finally 再次 Save-Receipt。
因此不能原样放进新正常执行路径，同时声称新路径的每个受管出口都遵守第7节。
旧源码/哈希/原始回执/审查保持冻结，不在本规范或文档提交中修改。

后续实现须在新隔离目录定义受出口管理器约束的拥有对象执行边界，保留原本
双流及时接入、确切对象终止/退出等待、共享排空期限和首因收束要求；禁止只包
住旧函数返回值却保留其内部绕过出口表的写入。不修改 codec/inbox/原 seam。
旧进程关联观察器可只读复用，不能因此宣称执行器已经通过新合同。

旧 PrimarySurvivesFinalReceiptFault 向量依赖对同一坏回执的两次失败写入；它与
新“不第二次访问”合同不兼容，不能照搬旧七组 oracle 宣称全新合同被验证。
新测试必须独立说明一次失败、后续访问被拒绝、首因和资源清理的观察。历史七组
结果仍保存为原合同的观察，不改判、不重建、不把新行为伪装成旧 oracle 相同。
原 seam 输出及完整 trace 继续作为无产品行为变化的独立回归边界。

## 10. 新接口边界与控制面

以后新入口分为启动明确批准的新会话、同一会话内的固定步骤推进、关闭/失败
收束以及只读证据导出。没有 LoadSessionFromJson、恢复旧确认或忽略失败继续的入口。
旧独立 Run -Slot/Integrate 的磁盘 Outcome 门不再是新序列的公开续跑入口。

外部控制如需要跨工具交互，只能选择未来计划冻结的固定步骤/停止命令；不得
接受任意命令、脚本块、故障 callback、伪造观察 setter 或动态产品开关。
命令本身只是推进请求，不能携带或覆盖完成确认。版本、来源或顺序不明即拒绝。
新控制面、宿主等待上限及新进程归属须在实施计划具体化并计入预算，不能借用
本规范作为长期监控、后台服务、产品运行或额外目标启动授权。

每个会话的源码冻结代次固定，不在存活监督器内原地修补已加载代码或动态重冻结。
RED→GREEN若需要实际源码修改，未来计划应明确分成两个独立授权序列：RED会话
完整结束并记录其消费；修改后以GREEN序列专属的新授权、固定输入和新监督器
开始。不能把旧RED文件或旧确认变成GREEN首步权限，也不能归还RED已消费额度。
两个宿主/两组目标均须纳入同一个待批准计划的精确预算，不能作为额外隐含进程。
每个序列内有后续步骤时仍只用该序列的存活确认；序列间没有恢复/迁移确认操作。
因此不引入动态源码修复控制命令。任何固定等待也须有期限；宿主丢失/未知进度
就结束该会话，不以恢复机制补跑。本稿没有批准这些未来序列或任何代码修改。

## 11. 验收所需证据（不是执行批准）

后续计划须为以下输入给出独立字面预期、实际消费者和明确运行次数：

| 情形 | 必须观察的结果 |
| --- | --- |
| 只有完整 EXPECTED_* 文件，无活确认 | 下一步拒绝，Start=0，不由文件重建确认 |
| 候选成功字节存在，但最终写入报告失败/unknown | 无确认、会话失败，不能继续；原件不被重写 |
| 写失败后进入 finally、汇总或再发布 | 清理执行；同一出口后续逻辑文件访问=0 |
| 缺失/坏 JSON、无效索引或转换失败 | 出口 Failed；不重建，首因不变，不能放行 |
| 输出首段/末段/flush/关闭失败 | 不发确认；不以已输出 PASS/候选成功当作继续权限 |
| 确认跨步、跨代次、跨会话、复制/重放 | 全部拒绝，Start=0；被消费确认不能再用 |
| 正常唯一完成及下一步 | 所有实际返回/校验满足后仅消费一次；无产品能力标记升级 |
| 进程启动后记账失败 | 确切对象有限退出/双流/释放；不重试失败台账，不发确认 |
| 预消费写入失败 | 本次已消费，但 Start=0；不自动重试或返还额度 |
| 次因超过8项、诊断/错误流失效 | 首因保留、有界终止；unknown/INCOMPLETE，不递归记录 |
| 会话死亡、新进程或换机读旧结果 | 只可恢复资料；不恢复运行状态或权限 |
| 新执行器健康/故障/超时及原 seam | 新独立完整 oracle、实际进程收束；原 seam 边界不变 |

必须区分：真实文件错误、纯状态消费断言、构造的“成功文件+缺确认”负例和实际
最终写入晚报错的动态诱发。不能把前者冒称最后一种已发生；若无法安全诱发，
应明确动态覆盖限制，并用真实消费入口拒绝残留成功文件、实际写失败后的无确认
及源码边界审查提供对应证据。任何缺口不靠 fabricated exception 或通用注入钩子
补成“已测”。资源/文件操作计数若作为观察，须指向实际受管边界并审查所有绕行。

## 12. 换机、预算与审阅关口

仓库保留新源码/测试、独立 oracle、已批准规范/计划、完整审查处置、原始数字
文本与字节/哈希、实际预算消费和剩余/冻结状态；ignored raw 留在原机，不从
便携摘要重建成“原件”。源码、证据和待办可恢复，内存引用、宿主身份、凭据及
运行权限不可恢复。恢复入口只读，不能自动续跑、新建会话重用旧批准或重复目标。
