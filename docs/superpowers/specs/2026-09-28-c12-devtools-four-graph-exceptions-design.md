# 开发工具隔离修订：四项图级版本的精确条件例外

日期：2026-09-28。
状态：用户已明确确认本文书面设计，随后确认对应实施计划修订及 R3b 四个 tools 候选精确准备范围。实施按获批计划接续，验收及安全门禁不变。

## 1. 目的与优先级

继续完成双模块隔离，同时保持业务、Goose 和五个开发工具实际使用的包及版本不变。只处理正常整理会删除显式约束的四项 tools 图级依赖，不把完整模块图比较改成仅比较实际包。

本文获书面批准并落实到获批实施计划后，仅替代 [原锁版本修订](2026-09-27-c12-devtools-version-lock-revision-design.md) 第 4/7 节中“tools 四项必须恢复且零例外”的条款，以及相关的例外总数描述。其余合同继续有效，历史证据不改写。

新版规则为：原 root 28 项仍须精确恢复；原三个 root 条件例外保持原范围和门槛；tools 仅增加本文四项条件例外。例外按 owner/path/version 识别，不共享到另一个模块，不允许其他版本、第五项 tools 例外或第四项 root 例外。

模块身份、Go 1.26.0 / go1.26.5、Goose 3.27.1、Buf 1.72.0、protoc-gen-go 1.36.11、oapi-codegen 2.8.0、sqlc 1.31.1、golangci-lint 2.12.2 均不变。保留 Native inline，修订原实施计划，不新建 worktree、不重做已完成的 Task 1。

## 2. 依据与限制

依据 [四项影响评估](../../roadmap/2026-09-28-devtools-four-version-assessment.md) 和 [恢复证据](../../roadmap/2026-09-27-devtools-version-lock-evidence.md)：四个显式 require 在工具目录正常离线 tidy 后全部被删除，四份锁文件恢复为试验前相同哈希。这只排除了该次显式约束方案，不证明所有可能方案均不可行。

四项在五工具的既有 Windows 实际包闭包中均无包，但上游源码确有引用：moby/moby/client v0.5.0 的 pkg/progress 使用 x/time/rate；pingcap/tidb/pkg/parser v0.0.0-20260418072757-ce92298d1124 的 goyacc 使用三个 modernc 模块。不能一概称为仅测试依赖或永远不会执行。

Goose 的既有实际包闭包使用 modernc.org/mathutil v1.7.1；该根模块版本必须保持。现有诊断选中值不是严格完整查询成功证据，历史专项绿色不证明新规则已满足。未检查的低版本源码差异、漏洞状态、第三方测试或其他平台均不得声称安全等价或验证通过。

## 4. 候选启用条件与失败关闭

每项较低候选须同时具备以下证据，缺一项即保持未验收：

1. 两模块严格离线完整模块查询及图解析成功，无 Error；不得用 -e 输出或忽略缺失记录判定成功。活动图能追溯到保留的父模块，而非只引用缓存中的孤立 go.mod。
2. 记录原值、候选值、活动父边、源码用途、显式恢复约束被 tidy 移除的证据，以及为何本方案在不改变实际用途的情况下选择该候选。证据不能仅以“没有报错”或“缓存里存在”代替。
3. 四项在五个实际工具闭包均不提供包；重新读取的八组 Windows 包集合及实际模块版本与原基线一致，root/Goose 的 mathutil v1.7.1 不变。读取与比较错误、Incomplete、DepsErrors 均失败。
4. 为该边界增加自动检查：候选一旦进入工具实际包闭包，即使 owner/path/version 恰在例外表内，也必须拒绝使用图级豁免。人工更新包基线不能静默绕过该用途审查。此检查不禁止 root 按原合同使用 mathutil。
5. 每个使用中的例外有来源校验和及可提交的必要性记录。证据 ID 必须非空、在指定证据文档中对应唯一存在的记录，并绑定正确 owner/path/version；记录内容仍须审阅，存在一个 ID 本身不是事实证明。
6. 正常 tidy 后，四份锁文件字节及重新读取的模块选择稳定；全部新增、删除及迁移有审核过的归属证据。不能从实际快照自动生成期望后自证通过。

出现未知新增、其他版本、缺失目标、跨归属例外、候选进入实际包、错误或不存在的证据记录、重复模块身份、额外差异，均明确失败。若恢复原版本，则按原版本比较，不强制使用较低候选。

## 5. 准备权限独立

本文书面确认只允许据此修订原实施计划，不立即执行下载或实现。此前对三个 root 候选的下载授权不覆盖本表四个较低版本。

修订计划须单列缺失时的精确准备清单：golang.org/x/time@v0.11.0、modernc.org/mathutil@v1.6.0、modernc.org/sortutil@v1.2.0、modernc.org/strutil@v1.2.0，并取得明确准备授权。可在审阅计划时同时批准该清单，但不能由仅确认本文推定。额外版本或传递准备需求超出清单时停止报告。

准备仍只使用官方 proxy.golang.org 与 sum.golang.org、固定 Go、独立最小备用模块；禁用 direct/VCS/auth 回退与私有绕过，不关闭校验，不执行下载内容、不修改生产锁文件。保持原 900 秒准备总预算，超时只停止自有进程。下载成功不等于候选安全、必要或验收通过。

正式验证仍禁网；缺失、篡改和查询错误必须失败，不在验收中补包。

## 6. 实施范围与回归要求

修改应集中于既有版本策略/比较器及其反例测试、归属与包用途检查、证据和原实施计划；模块变化必须与该任务原边界一致。666 条模块基线、八组原包映射及原保护哈希保持不可变，不以当前低版本重写基线。

测试至少覆盖四个精确 tools 候选、保留原值、较低候选错误版本、例外被用于 root、第五项 tools 例外、四目标之一缺失、进入实际工具包闭包、仅 root 合法使用 mathutil、缺失/错误/重复证据 ID、未审核归属和严格查询错误。原三个 root 候选及原 28 项恢复反例保留。现有 35 项回放应区分“精确值且条件齐备”与“仅版本碰巧匹配但证据不足”，不能把旧反例整体删掉。

仍须完成两模块完整性校验、重复 tidy 稳定性、八组包比较、52 个受保护文件不变、全部适用脚本专项、根专属 lint fixture、真实工具版本、生成无差异、真实根 lint 和最终独立审查。沿用 90 秒元数据诊断、900 秒工具验证、原专项及 C11 嵌套阶段预算，不新增跳过或提高时限。

不添加虚构 import/tool、跨模块 require、go.work、replace/exclude，不回挂无实际用途的根专属依赖，不改第三方清单或缓存，不修改生产逻辑、SQL、runner、smoke、生成内容及 Docker 资源协议。正常 tidy 需在所属模块目录运行，不能把根源码误解释为工具模块。
